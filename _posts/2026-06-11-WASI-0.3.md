**WASI 0.3 is official, and async is now native to WebAssembly Components.** The WASI Subgroup voted to ratify WASI 0.3.0, rebasing WASI onto the WebAssembly Component Model's async primitives. The 0.3.0 spec is stable, and runtime and toolchain support is landing now.

The work that `wasi:io` in WASI 0.2 used to do (pollables, input-streams, output-streams) has been pushed down into [the canonical ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md), where the Component Model now offers these primitives natively.

If you look at the WIT diff between WASI 0.2 and WASI 0.3, most of what changed across `wasi:cli`, `wasi:filesystem`, `wasi:http`, and `wasi:sockets` is a consequence of building atop native async in the Component Model. The interfaces look different because they no longer have to carry their own async machinery.

The new primitives for this `async func`, `stream<T>`, and `future<T>`, live in the Component Model's [canonical ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md), allowing bindings generators to emit idiomatic async bindings in their given language.

## Why rebase on the Component Model's async ABI?

In WASI 0.2 each component needed its own event loop/async runtime. That meant that individual components could be run on a host, but there was no way for those event loops to coordinate with one another. This is why WASI 0.2 could express async components but not support native async composability.

WASI 0.3 makes it so the host is now the one in charge of managing the one event loop that is shared by all components.

### What the Component Model ABI gives us

The Component Model now has `stream<T>`, `future<T>`, and `async` as first-class constructs in the canonical ABI:

- `stream<T>` and `future<T>` are built-in to the canonical ABI. Like a resource, each is an owned handle, passing one across a component boundary transfers ownership from caller to callee, but unlike a resource it can't be borrowed, and the type itself is part of the Component Model rather than something a component imports or exports.
- The runtime, not each component, drives the scheduling. When a value has been delivered to a `future`, the runtime schedules whichever task is awaiting it, regardless of how many component boundaries sit between them. The writer that delivers that value might be the host, another component, or even the same component that holds the read end.
- Components export and import `async func`s directly, so the `start-foo` / `finish-foo` / `subscribe` three-step from WASI 0.2 disappears.
- The async model is *completion-based*, not *readiness-based*. This is similar to the ultra-efficient Linux `io_uring` and Windows' IOCP/`IoRing` APIs. An `epoll`/`kqueue`-style readiness API can be emulated on top of this for programs which need the compatibility.

## What this looks like in the WIT

Most of the changes in the 0.3 interfaces are entirely mechanical. WASI 0.2 had to perform some acrobatics to make async work, but now that async is native to the component model we can write the same things we did before but much more ergonomically. Here is a overview of the patterns we were encoding in WASI 0.2 with the `wasi:io` package, and what those patterns now look like in 0.3 with Component Model async:

| WASI 0.2 (`wasi:io`)       | WASI 0.3 (Component Model)             |
| -------------------------- | -------------------------------------- |
| `resource pollable`        | `future<T>`                            |
| `resource input-stream`    | `stream<u8>`                           |
| `resource output-stream`   | `stream<u8>` (written-to direction)    |
| `poll(list<pollable>)`     | `await` on a future (runtime-handled)  |
| `subscribe()` on resource  | return a `future<...>` from the call   |
| `start-foo` / `finish-foo` | `foo: async func(...)`                 |

A problem with WASI 0.2 was that it surfaced terminal errors inline on each read call on the stream. That meant callers only learned the outcome if they kept reading. If readers stopped early they could not distinguish between a stream close and an error.
In WASI 0.3 streams now return an additional future which resolves independently of how much of the stream is consumed, solving the stream status problem of WASI 0.2:

```wit
// WASI 0.2
read-via-stream: func() -> result<input-stream, error-code>;
// WASI 0.3
read-via-stream: func() -> tuple<stream<u8>, future<result<_, error-code>>>;
```

Let's take a deeper look at `wasi:http` as this is the most visible reorganization of the release.

**Resources collapsed from 8 to 2.** WASI 0.2 had a full matrix of resources for the incoming/outgoing × request/response/body space, plus two async-specific ones:

- `incoming-request`, `outgoing-request`
- `incoming-response`, `outgoing-response`
- `incoming-body`, `outgoing-body`
- `future-trailers`, `future-incoming-response`

WASI 0.3 has just `request` and `response`, with bodies represented as `stream<u8>`.

**The handler is an async function.** WASI 0.2's `incoming-handler` used a `response-outparam` parameter to work around the lack of native async returns:

```wit
// WASI 0.2
interface incoming-handler {
  handle: func(request: incoming-request, response-out: response-outparam);
}

// WASI 0.3
interface handler {
  handle: async func(request: request) -> result<response, error-code>;
}
```

The outgoing side mirrors it:

```wit
interface client {
  send: async func(request: request) -> result<response, error-code>;
}
```

**New worlds for middleware.** The old `proxy` world is replaced by `service`, plus a `middleware` world that both imports and exports `handler`. That gives first-class support to components sitting in a request path:

```wit
world service {
  include wasi:clocks/imports@0.3.0;
  include wasi:random/imports@0.3.0;
  import wasi:cli/stdout;
  import wasi:cli/stderr;
  import wasi:cli/stdin;
  import client;
  export handler;
}

world middleware {
  include service;
  import handler;  // upstream
}
```

With this new `middleware` world, users can easily perform [service chaining](https://bytecodealliance.org/articles/how-wasm-components-enable-pluggable-middleware), a pattern where components are composed together, communicating over the `wasi:http/handler` interface. This means components acting as microservices that frequently interopt with other microservices, do not need to drop out to the network, but instead may be safely handled in the same process. For most microservices, this will be six orders of magnitude difference performance, milliseconds vs nanoseconds.

## Idiomatic async bindings

An interface like the `handler` interface in `wasi:http` lands in each guest language as that language's own async type.

```wit
interface handler {
  handle: async func(request: request) -> result<response, error-code>;
}
```

In Rust:

```rust
use wasi::http::types::{ErrorCode, Request, Response};

impl Guest for Component {
    async fn handle(request: Request) -> Result<Response, ErrorCode> {
        // ...
    }
}
```

In JavaScript:

```javascript
import { Response } from 'wasi:http/types';

export const handler = {
  async handle(request) {
    // ...
    return new Response(/* ... */);
  },
};
```

In Python:

```python
from wasi.http.types import Request, Response

class Handler:
    async def handle(self, request: Request) -> Response:
        # ...
```

Rust, JavaScript, and Python all build on *stackless* coroutines, where the compiler rewrites an `async` function into a state machine. Go takes the other approach: a goroutine is a *stackful* coroutine that blocks on ordinary, synchronous-looking calls. The Component Model's async ABI accommodates both just as cleanly. With [componentize-go](https://github.com/bytecodealliance/componentize-go) and the [wit-bindgen](https://github.com/bytecodealliance/wit-bindgen) Go generator, the exported `handle` is a plain function that returns a value, and streaming bodies are produced from goroutines doing blocking calls. The runtime parks the goroutine at the ABI boundary and resumes it when the stream is ready, without blocking the rest of the program:

```go
package export_wasi_http_handler

import (
	. "wit_component/wasi_http_types"
	. "go.bytecodealliance.org/pkg/wit/types"
)

func Handle(request *Request) Result[*Response, ErrorCode] {
	tx, rx := MakeStreamU8()
	go func() {
		defer tx.Drop()
		tx.WriteAll([]uint8("Hello, world!"))
	}()

	response, send := ResponseNew(
		FieldsFromList([]Tuple2[string, []byte]{
			{F0: "content-type", F1: []byte("text/plain")},
		}).Ok(),
		Some(rx),
		trailersFuture(),
	)
	send.Drop()

	return Ok[*Response, ErrorCode](response)
}
```

Guests don't have to learn a WASI-specific I/O on top of the async model they already use. Whether the language models concurrency with stackless or stackful coroutines, the ABI is shared. What developers see is native to their language of choice.

## Where we are right now

- **Spec ratified.** WASI 0.3 has passed the Subgroup vote. This is a stable release with additional additive, non-breaking changes in patch release, e.g. 0.3.x.
- **Wasmtime support landing.** Wasmtime 45 runs the latest release candidate today, and Wasmtime 46 will ship WASI 0.3.0 with Component Model Async enabled by default.
- **jco close behind.** jco, the JavaScript Component Model toolchain and our second reference implementation, also supports the latest release candidate today, with official 0.3.0 release support landing now.
- **Guest toolchains next.** In parallel, we're working to enable WASI 0.3 in the guest toolchains, so you'll be able to write WASI 0.3 components in Rust, Go, JavaScript, Python, and more.

If you build WASI components, or tooling that targets them, now is the time to build on WASI 0.3.0. Run your components against Wasmtime, try them against jco, and tell us what you build. WASI 0.3 is here, with async and composability built on the Component Model's native primitives.
