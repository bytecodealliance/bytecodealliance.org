**WASI 0.3 is official, and async is now native to WebAssembly Components.** The WASI Subgroup voted to ratify WASI 0.3.0, rebasing WASI onto the WebAssembly Component Model's async primitives. The 0.3.0 spec is stable, and runtime and toolchain support is landing now.

The work that `wasi:io` in WASIP2 used to do (pollables, input-streams, output-streams) has been pushed down into [the canonical ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md), where the Component Model now offers these primitives natively.

If you look at the WIT diff between WASI 0.2 and WASI 0.3, most of what changed across `wasi:cli`, `wasi:filesystem`, `wasi:http`, and `wasi:sockets` is a consequence of building atop native async in the Component Model. The interfaces look different because they no longer have to carry their own async machinery.

The new primitives for this `async func`, `stream<T>`, and `future<T>`, live in the Component Model's [canonical ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md), allowing bindings generators to emit idiomatic async bindings in their given language.

## Why rebase on the Component Model's async ABI?

### The sandwich problem

In WASI 0.2, async is a `pollable` resource with the majority of the management of that resource in `wasi:io`. This worked well for cases where components are linked directly to the host or to one other component. There is only one `pollable`, owned, in many cases by the host, and the host runs the event loop.

It breaks the moment a component sits in the middle. Picture a three-layer sandwich:

```
  ┌─────────────────────────────┐
  │  Component A                │   awaits work
  │                             │
  │   pollable_B ───────────────┼──┐
  └─────────────────────────────┘  │  (A can only see B's pollable)
                                   │
  ┌─────────────────────────────┐  │
  │  Component B                │◀─┘
  │  (middle)                   │
  │                             │
  │   pollable_host ────────────┼──┐
  └─────────────────────────────┘  │  (the real readiness lives here)
                                   │
  ┌─────────────────────────────┐  │
  │  Host                       │◀─┘
  │                             │
  │  wake ⇒ pollable_host ready │
  └─────────────────────────────┘
```

`pollable_host` is a resource inside B's instance. A cannot hold it, poll it, or name it. The best B can do is hand A its own `pollable_B` and promise to flip it when `pollable_host` fires, but there is no ABI hook for "when this pollable becomes ready, run this code in B." B would have to be scheduled and actively polling just to forward the wake-up. In practice the callback chain from host to B to A gets dropped on the floor, and the wake-up is lost in the middle of the sandwich.

This is why WASI 0.2 could express async components but not support native async composability.

### What the Component Model ABI gives us

The Component Model now has `stream<T>`, `future<T>`, and `async` as first-class constructs in the canonical ABI:

- `stream<T>` and `future<T>` are built-in to the canonical ABI. Like a resource, each is an owned handle, passing one across a component boundary transfers ownership from caller to callee, but unlike a resource it can't be borrowed, and the type itself is part of the Component Model rather than something a component imports or exports.
- The runtime, not each component, drives the scheduling. When a value has been delivered to a `future`, the runtime schedules whichever task is awaiting it, regardless of how many component boundaries sit between them. The writer that delivers that value might be the host, another component, or even the same component that holds the read end.
- Components export and import `async func`s directly, so the `start-foo` / `finish-foo` / `subscribe` three-step from WASI 0.2 disappears.
- The async model is *completion-based*, not *readiness-based*. This is similar to the ultra-efficient Linux `io_uring` and Windows' IOCP/`IoRing` APIs. An `epoll`/`kqueue`-style readiness API can be emulated on top of this for programs which need the compatibility.

The middle component in our sandwich now passes the future through. There is no wake-up to forward and nothing for B to plumb by hand.

## What this looks like in the WIT

Most of the changes in the 0.3 interfaces are entirely mechanical. WASI 0.2 had to perform some acrobatics to make async work, but now that async is native to the component model we can write the same things we did before but much more ergonomically. Here is a overview of the patterns we were encoding in WASI 0.2 with the `wasi:io` package, and what those patterns now look like in 0.3 with Component Model async:

| WASI 0.2 (`wasi:io`)       | WASI 0.3 (Component Model)             |
| -------------------------- | -------------------------------------- |
| `resource pollable`        | `future<T>`                            |
| `resource input-stream`    | `stream<u8>`                           |
| `resource output-stream`   | `stream<u8>` (written-to direction)    |
| `poll(list<pollable>)`     | `await` on a future (runtime-handled)  |
| `subscribe()` on resource  | return a `future<...>` from the call   |
| `start-foo` / `finish-foo` | `foo: async func(...)`                 |

One more pattern to know about before we dive into specific packages. The common "give me a stream for this resource" call now returns both a stream and a completion future:

```wit
// WASI 0.2
read-via-stream: func() -> result<input-stream, error-code>;

// WASI 0.3
read-via-stream: func() -> tuple<stream<u8>, future<result<_, error-code>>>;
```

WASIP2 did surface terminal errors, but inline with each read call on the stream (via the stream-error variant). That meant callers only learned the outcome if they kept reading. Stop early and you never find out if the stream errored or just closed. In WASIP3 the future resolves independently of how much of the stream you consume, and it's a first-class async value you can await, forward across components, or compose with other futures.

### `wasi:io` — removed

This package is no longer needed. Every consumer uses the Component Model's native types.

### `wasi:cli`

Structurally the files are the same (`stdin.wit`, `stdout.wit`, `stderr.wit`,
`run.wit`, `exit.wit`, `terminal.wit`, `environment.wit`). The interesting
change is `stdio`.

```wit
// WASI 0.2
interface stdin {
  use wasi:io/streams.{input-stream};
  get-stdin: func() -> input-stream;
}

interface stdout {
  use wasi:io/streams.{output-stream};
  get-stdout: func() -> output-stream;
}

// WASI 0.3
interface stdin {
  use types.{error-code};
  read-via-stream: func() -> tuple<stream<u8>, future<result<_, error-code>>>;
}

interface stdout {
  use types.{error-code};
  write-via-stream: func(data: stream<u8>) -> future<result<_, error-code>>;
}
```

Note the direction flip on stdout. WASI 0.2 handed you an `output-stream` that you wrote into imperatively. WASI 0.3 has you pass in a `stream<u8>` and get back a future that resolves when the write completes. A small new `wasi:cli/types` interface carries a shared `error-code` variant (`io`, `illegal-byte-sequence`, `pipe`).

### `wasi:sockets`

**The `network` resource is gone.** WASI 0.2 modeled network access as a capability resource threaded through every bind/connect/lookup call. WASI 0.3 removes it entirely; network access is granted via world imports.

**Every start/finish pair became one `async func`.** The in-progress intermediate states (`bind-in-progress`, `connect-in-progress`, `listen-in-progress`) and the `subscribe() -> pollable` that drove them are gone:

```wit
// WASI 0.2
start-bind:     func(network: borrow<network>, local: ip-socket-address)
                 -> result<_, error-code>;
finish-bind:    func() -> result<_, error-code>;
start-connect:  func(network: borrow<network>, remote: ip-socket-address)
                 -> result<_, error-code>;
finish-connect: func()
                 -> result<tuple<input-stream, output-stream>, error-code>;

// WASI 0.3
bind:    async func(local-address: ip-socket-address)  -> result<_, error-code>;
connect: async func(remote-address: ip-socket-address) -> result<_, error-code>;
listen:  async func()                                  -> result<_, error-code>;
accept:  async func()
  -> result<tuple<tcp-socket, ip-socket-address>, error-code>;
```

Note that WASI 0.2's `finish-connect` returned the TCP stream pair inline. In WASI 0.3 `connect` returns nothing special; byte I/O lives on the socket resource's own stream methods.

UDP got the same treatment. The incoming/outgoing datagram stream resources are gone, replaced by plain `async send` and `async receive`. Error codes across TCP, UDP, and name-lookup were unified into a single `error-code` variant, with a new `connection-broken` case and an open-ended `other(option<string>)` tail.

### `wasi:http` — unified `request`/`response` and `handler`

This is the most visible reorganization of the release.

**Resources collapsed from 8 to 2.** WASI 0.2 had a full matrix of resources for the incoming/outgoing × request/response/body space, plus two async-specific ones:

- `incoming-request`, `outgoing-request`
- `incoming-response`, `outgoing-response`
- `incoming-body`, `outgoing-body`
- `future-trailers`, `future-incoming-response`

WASI 0.3 has just `request` and `response`, with bodies represented as
`stream<u8>` directly and trailers as a `future<result<option<trailers>, error-code>>`. `future-incoming-response` vanishes because a plain `future<result<response, error-code>>` does that job now.

**The handler is an async function.** WASI 0.2's `incoming-handler` used a `response-outparam` parameter to work around the lack of native async returns:

```wit
// WASI 0.2
interface incoming-handler {
  handle: func(request: incoming-request, response-out: response-outparam);
}

// WASI 0.3
interface handler {
  handle: async func(request: request) -> result<response, error-code>;
}
```

The outgoing side mirrors it:

```wit
interface client {
  send: async func(request: request) -> result<response, error-code>;
}
```

**New worlds for middleware.** The old `proxy` world is replaced by `service`, plus a `middleware` world that both imports and exports `handler`. That gives first-class support to components sitting in a request path:

```wit
world service {
  include wasi:clocks/imports@0.3.0;
  include wasi:random/imports@0.3.0;
  import wasi:cli/stdout;
  import wasi:cli/stderr;
  import wasi:cli/stdin;
  import client;
  export handler;
}

world middleware {
  include service;
  import handler;  // upstream
}
```

### `wasi:filesystem`

**Streaming reads/writes** switched to the stream-plus-future shape:

```wit
// WASI 0.2
read-via-stream:  func(offset: filesize) -> result<input-stream, error-code>;
write-via-stream: func(offset: filesize) -> result<output-stream, error-code>;

// WASI 0.3
read-via-stream:  func(offset: filesize)
  -> tuple<stream<u8>, future<result<_, error-code>>>;
write-via-stream: func(data: stream<u8>, offset: filesize)
  -> future<result<_, error-code>>;
```

**Directory iteration** switched from a resource-based iterator to a stream:

```wit
// WASI 0.2
read-directory: func() -> result<directory-entry-stream, error-code>;
// plus: resource directory-entry-stream { read-directory-entry: func() -> ... }

// WASI 0.3
read-directory: func()
  -> tuple<stream<directory-entry>, future<result<_, error-code>>>;
```

### `wasi:clocks`

The `wasi:clocks` changes are, deliberately, mostly renames. Flagging them because the churn shows up in downstream suites.

[WASI#79 (Avoid nonstandard use of names for types)](https://github.com/WebAssembly/WASI/pull/79) moved the package onto conventional names: `wall-clock` became `system-clock`, and `datetime` became `instant`. The motivation was consistency with how the rest of the ecosystem talks about clocks. "Wall clock" and "datetime" were WASI-isms that didn't match POSIX, Rust's `std::time`, or most other systems. `wasi:filesystem` timestamps followed, for the same reason.

A small `types.wit` was added to share the `duration = u64` alias. `monotonic-clock` also dropped its pollable-returning `subscribe-instant` and `subscribe-duration` calls; callers now `await` a host-provided timer future, the same pattern used everywhere else.

Downstream impact is mostly mechanical find-and-replace. See
[WebAssembly/wasi-testsuite@f13976f](https://github.com/WebAssembly/wasi-testsuite/commit/f13976fec4d8ba72340c646383f76cb6cb257c93#diff-f8fc73d9e9844ad1bf5e3d275a478dbca0aac08790037d74b7a3a55d097abfb6) for a representative update across the test suite.

## Idiomatic async bindings

An interface like the `handler` interface in `wasi:http` lands in each guest language as that language's own async type.

```wit
interface handler {
  handle: async func(request: request) -> result<response, error-code>;
}
```

In Rust:

```rust
use wasi::http::types::{ErrorCode, Request, Response};

impl Guest for Component {
    async fn handle(request: Request) -> Result<Response, ErrorCode> {
        // ...
    }
}
```

In JavaScript:

```javascript
import { Response } from 'wasi:http/types';

export const handler = {
  async handle(request) {
    // ...
    return new Response(/* ... */);
  },
};
```

In Python:

```python
from wasi.http.types import Request, Response

class Handler:
    async def handle(self, request: Request) -> Response:
        # ...
```

Rust, JavaScript, and Python all build on *stackless* coroutines, where the compiler rewrites an `async` function into a state machine. Go takes the other approach: a goroutine is a *stackful* coroutine that blocks on ordinary, synchronous-looking calls. The Component Model's async ABI accommodates both just as cleanly. With [componentize-go](https://github.com/bytecodealliance/componentize-go) and the [wit-bindgen](https://github.com/bytecodealliance/wit-bindgen) Go generator, the exported `handle` is a plain function that returns a value, and streaming bodies are produced from goroutines doing blocking calls. The runtime parks the goroutine at the ABI boundary and resumes it when the stream is ready, without blocking the rest of the program:

```go
package export_wasi_http_handler

import (
	. "wit_component/wasi_http_types"
	. "go.bytecodealliance.org/pkg/wit/types"
)

func Handle(request *Request) Result[*Response, ErrorCode] {
	tx, rx := MakeStreamU8()
	go func() {
		defer tx.Drop()
		tx.WriteAll([]uint8("Hello, world!"))
	}()

	response, send := ResponseNew(
		FieldsFromList([]Tuple2[string, []byte]{
			{F0: "content-type", F1: []byte("text/plain")},
		}).Ok(),
		Some(rx),
		trailersFuture(),
	)
	send.Drop()

	return Ok[*Response, ErrorCode](response)
}
```

Guests don't have to learn a WASI-specific I/O on top of the async model they already use. Whether the language models concurrency with stackless or stackful coroutines, the ABI is shared; what developers see is native to their language of choice.

## Where we are right now

- **Spec ratified.** WASI 0.3 has passed the Subgroup vote. This is a stable release with additional additive, non-breaking changes in patch release, e.g. 0.3.x.
- **Wasmtime support landing.** Wasmtime 45 runs the latest release candidate today, and Wasmtime 46 will ship WASI 0.3.0 with Component Model Async enabled by default.
- **jco close behind.** jco, the JavaScript Component Model toolchain and our second reference implementation, also supports the latest release candidate today, with official 0.3.0 release support landing now.
- **Guest toolchains next.** In parallel, we're working to enable WASIp3 in the guest toolchains, so you'll be able to write WASI 0.3 components in Rust, Go, JavaScript, Python, and more.

If you build WASI components, or tooling that targets them, now is the time to build on WASI 0.3.0. Run your components against Wasmtime, try them against jco, and tell us what you build. WASI 0.3 is here, with async and composability built on the Component Model's native primitives.
